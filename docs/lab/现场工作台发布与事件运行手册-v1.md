# 现场工作台发布与事件运行手册 v1

本手册用于 Agentic Football 工作台的活动前 release gate、feedback/live 环境核对、可恢复初始化、事件日运行、镜像回滚、SQLite 恢复和断网离线查看。

## 1. 事实、假设与待确认边界

### 已确认的仓库事实

- 当前应用通过 `lightsail/server.mjs` 运行同一套 Worker 业务逻辑，活动状态保存在 SQLite `event_state` 中。
- feedback 和 live 使用不同 Compose/volume 定义；应用镜像更新不会自动清空数据卷。
- `.github/workflows/test-and-deploy-feedback.yml` 对每个 push 运行测试；只有 `main` 且 `FEEDBACK_HOSTED_DEPLOY_ENABLED=true` 时才部署 feedback。
- feedback 强制部署脚本会在候选容器健康检查失败时恢复上一个镜像；该动作不回滚数据。
- `npm run acceptance:release` 会分别为 24 队和 32 队创建全新临时 SQLite 与随机本机端口，跑到唯一冠军，结束后删除临时环境。
- `npm run ops:export-offline` 只读取显式指定的 SQLite 副本，输出字段白名单 JSON 和单文件 HTML；它不是数据库备份或恢复工具。

### 团队工作假设

- feedback 用于内部验收，live 用于正式活动；两者不得共享 volume、PIN 或浏览器验收结论。
- 活动正式开始前采用“一场活动一套新状态”的方式；旧状态先停写备份，再可恢复地移入同一 volume 的 `archive/`。
- 现场断网时，离线包只承担查看队伍、冻结名单、赛程和比分的只读兜底；恢复联网后以 SQLite 主状态为准。

### 待 SA 或同事确认

- live 的最终域名、Compose project name、数据 volume 名称和主机备份目录。
- AWS Workshop/Game Portal Code 被使用后的真实消耗、补发和回收规则。
- 活动现场谁有权批准 live 数据 reset/restore，以及双人复核名单。

这些未确认项不能由本手册中的示例值替代。

## 2. Git 交付与证据规则

每次候选发布必须对应一个明确 Git SHA。功能、测试、数据构造和 runbook 应拆为可单独 `git revert` 的提交；不得使用 `git reset --hard` 清理现场分支。

候选分支检查：

```bash
git status --short
git log --oneline --decorate -12
git diff --check
```

必须确认：

1. 只包含本次候选变更，不吸收个人调试文件、真实 `.env`、PIN、Code、SQLite 或 Playwright 输出。
2. 每个提交都能说明独立目的和对应测试。
3. 本地通过只代表本地；push 后的 GitHub Actions、feedback 部署、live 部署分别记录证据，不互相替代。

代码回退使用：

```bash
git revert <single-commit-sha>
```

先在新分支验证 revert 和完整命令集，再按正常发布流程推进；不要在服务器直接修改仓库文件冒充 Git 交付。

## 3. 本地 release gate

首次准备：

```bash
npm ci
```

候选 SHA 的标准验证：

```bash
npm run lint
npm test
npm run acceptance:release
npm run acceptance:release
```

第二次 `acceptance:release` 用来确认：

- 端口和临时 SQLite 均重新创建；
- 24/32 队都从 `T-001` 开始，无历史数据串扰；
- 24 队为 6 个四队组、36 场小组赛、4 个 bye、11 场实际淘汰赛；
- 32 队为 8 个四队组、48 场小组赛、无 bye、15 场实际淘汰赛；
- 两种规模每队都打 3 场小组赛，最后只有一个冠军；
- stdout JSON 不包含测试 Code/PIN。

交互验收按需启动：

```bash
npm run acceptance:serve -- --scenario journey --port 4310
npm run acceptance:serve -- --scenario tournament-knockout --port 4311
```

每个交互场景使用临时 SQLite。端口被占用时必须换端口，不能复用来历不明的旧服务。

## 4. feedback 与 live 证据分层

### feedback

当前 workflow 的 feedback 公网健康检查为：

```bash
curl --fail --silent --show-error --connect-timeout 8 --max-time 15 \
  https://afc.awscommunity.cn/healthz
```

还需记录：Git SHA、GitHub Actions run、部署完成时间、浏览器验收账号类型和关键截图。健康检查成功只证明进程/SQLite 可用，不证明权限矩阵和完整赛事已验收。

### live

live 必须使用同一候选 SHA 重新执行健康检查和浏览器 smoke test。域名、主机、Compose project、volume 与 PIN 由活动负责人明确填写；禁止把 feedback 结果直接标记为 live 通过。

live smoke test 至少包括：

1. 匿名 `/api/maintenance/snapshot` 为 `404`。
2. participant 只看到本队 Code；其他参与者和 display 不出现 canary Code/PIN。
3. Staff 可查看绑定 Code、接单/解决求助、首次录入赛果。
4. Admin 更正赛果必须填原因；存在已完成下游时返回 `409` 且状态不变。
5. live `/healthz`、参与者首页、Staff 和 display 都可访问。

## 5. SQLite 备份、初始化与恢复

### 5.1 操作门禁

任何 feedback/live 数据操作前都必须记录：目标环境、主机、Compose 文件、app container、volume、候选 SHA、操作人、复核人和回滚包路径。不能使用默认环境推断。

feedback 当前已确认值：

```bash
AFC_PROJECT=agentic-football-feedback
AFC_COMPOSE=/home/ubuntu/agentic-football-event-ops/lightsail/docker-compose.feedback-ip.yml
AFC_APP_CONTAINER=agentic-football-feedback
AFC_DATA_VOLUME=agentic-football-feedback-data
AFC_BACKUP_DIR=/home/ubuntu/afc-backups/feedback
AFC_STAMP=$(date -u +%Y%m%dT%H%M%SZ)
```

live 不提供猜测值。先在主机上用 `docker compose ... config` 和 `docker volume ls` 核对，再显式填写同名变量。

### 5.2 停写备份

```bash
sudo docker compose -p "$AFC_PROJECT" -f "$AFC_COMPOSE" stop app
sudo install -d -m 700 "$AFC_BACKUP_DIR"
AFC_VOLUME_MOUNT=$(sudo docker volume inspect --format '{{.Mountpoint}}' "$AFC_DATA_VOLUME")
sudo tar --exclude='./archive' -C "$AFC_VOLUME_MOUNT" -czf \
  "$AFC_BACKUP_DIR/event-$AFC_STAMP.tgz" .
sudo sha256sum "$AFC_BACKUP_DIR/event-$AFC_STAMP.tgz" | \
  sudo tee "$AFC_BACKUP_DIR/event-$AFC_STAMP.tgz.sha256"
sudo docker compose -p "$AFC_PROJECT" -f "$AFC_COMPOSE" start app
```

先停止 app 是为了避免只复制 `event.db` 而遗漏 WAL 中尚未 checkpoint 的写入。备份完成后检查文件非空、hash 文件存在、app 恢复 healthy。

### 5.3 可恢复的新活动初始化

这一步必须获得目标环境 reset 批准。它不删除旧数据库，而是把 SQLite 主文件/WAL/SHM 移入同 volume 的时间戳归档：

```bash
sudo docker compose -p "$AFC_PROJECT" -f "$AFC_COMPOSE" stop app
AFC_VOLUME_MOUNT=$(sudo docker volume inspect --format '{{.Mountpoint}}' "$AFC_DATA_VOLUME")
AFC_ARCHIVE_DIR="$AFC_VOLUME_MOUNT/archive/$AFC_STAMP"
sudo install -d -m 700 "$AFC_ARCHIVE_DIR"
sudo find "$AFC_VOLUME_MOUNT" -maxdepth 1 -type f -name 'event.db*' \
  -exec mv -t "$AFC_ARCHIVE_DIR" {} +
sudo docker compose -p "$AFC_PROJECT" -f "$AFC_COMPOSE" start app
```

启动后先检查 `/healthz`，再用 Staff 查看参与者/队伍为空。若不为空，立即停止，不得继续导入真实 Code。

### 5.4 数据恢复

恢复前再次停写并把当前 `event.db*` 移入新的归档目录；随后校验备份 hash，再将备份解压到已核对的 volume mount：

```bash
sudo docker compose -p "$AFC_PROJECT" -f "$AFC_COMPOSE" stop app
sudo sha256sum -c "$AFC_BACKUP_DIR/event-<approved-stamp>.tgz.sha256"
AFC_VOLUME_MOUNT=$(sudo docker volume inspect --format '{{.Mountpoint}}' "$AFC_DATA_VOLUME")
AFC_RESTORE_ARCHIVE="$AFC_VOLUME_MOUNT/archive/restore-$AFC_STAMP"
sudo install -d -m 700 "$AFC_RESTORE_ARCHIVE"
sudo find "$AFC_VOLUME_MOUNT" -maxdepth 1 -type f -name 'event.db*' \
  -exec mv -t "$AFC_RESTORE_ARCHIVE" {} +
sudo tar -C "$AFC_VOLUME_MOUNT" -xzf \
  "$AFC_BACKUP_DIR/event-<approved-stamp>.tgz"
sudo docker compose -p "$AFC_PROJECT" -f "$AFC_COMPOSE" start app
```

恢复后按 health → Staff counts → 抽样 participant → tournament/display 的顺序 readback。任何不一致都停止写入并保留恢复前后的两份归档。

## 6. 镜像回滚与数据回滚必须分开

- 镜像回滚：恢复上一 Git 构建产物，保留当前 volume。适用于新代码无法启动或 UI/API 回归。
- 数据恢复：从已校验 SQLite 备份恢复。适用于误操作或错误 reset；必须停写。
- 两者都需要时：先停止写入，固定数据库备份，再回滚镜像，最后由负责人决定是否恢复数据。

feedback 强制部署脚本在候选健康检查失败时会自动恢复 `previous_image`。手工回滚前先记录当前/上一镜像：

```bash
sudo docker inspect --format '{{.Config.Image}}' "$AFC_APP_CONTAINER"
sudo docker image ls agentic-football-event-ops --no-trunc
AFC_PREVIOUS_IMAGE=<verified-immutable-image-tag>
sudo env APP_IMAGE="$AFC_PREVIOUS_IMAGE" docker compose \
  -p "$AFC_PROJECT" -f "$AFC_COMPOSE" \
  up -d --no-deps --force-recreate app
```

不得用 `latest` 猜测 `AFC_PREVIOUS_IMAGE`，也不得顺手清空 volume。容器恢复 healthy 后仍需执行角色 smoke test，因为镜像健康不代表业务数据兼容。

## 7. 脱敏离线运营包

离线包应从“已经停写并复制到操作机”的 SQLite 副本生成，不要直接读取仍在写入的 live 文件：

```bash
npm run ops:export-offline -- \
  --db /absolute/path/to/copied/event.db \
  --output-dir /absolute/path/to/new/offline-event-20260724
```

`--output-dir` 必须不存在；脚本拒绝覆盖。输出：

- `offline-ops.json`：机器可读白名单数据。
- `index.html`：可直接在断网浏览器打开的只读页面。

允许字段：活动名、版本、队号、状态、资格、成员显示名/现场编号、冻结名单、小组、积分、赛程、比分、冠军、资源数量。

禁止字段：Workshop/Game Portal Code、PIN、client/session/token、反馈、审计详情、Workshop 备注。自动测试会用 canary 值和 key blacklist 验证两种输出。

离线包不能导回系统，也不能替代 `.tgz + sha256` SQLite 备份。

## 8. 事件日检查清单

### 开场前

- [ ] 确认 live SHA 与已通过 release gate 的 SHA 一致。
- [ ] 确认 feedback/live volume 不同，maintenance snapshot 关闭。
- [ ] 完成一次停写备份并校验 hash。
- [ ] 在获批后初始化新活动，readback 参与者/队伍为空。
- [ ] 只在 live 空状态确认后导入真实 Code；不把 Code/PIN 写入 Git、日志、截图或离线包。
- [ ] Staff、Admin、participant、display 四个表面分别 smoke test。
- [ ] 生成一次离线运营包并交给指定现场设备，验证 `index.html` 可断网打开。

### 比赛进行中

- [ ] Staff 首次录入；更正必须由 Admin 填写原因。
- [ ] 更正返回 `409` 时不强行覆盖，先确认是否已有完成下游。
- [ ] participant 求助必须先接单再解决；现场交接看 active queue。
- [ ] 资格确认只走 TA 专用动作，撤销只走 Admin 动作。
- [ ] 关键阶段（冻结、分组完成、淘汰赛生成、冠军）后记录只读截图和 Git/环境证据，不记录 Code。

### 活动结束

- [ ] 关闭发码、资格和赛程编辑开关，确认 maintenance snapshot 仍关闭。
- [ ] 停写生成最终 SQLite 备份和 hash。
- [ ] 生成最终脱敏离线包。
- [ ] 记录最终 SHA、数据库版本、冠军、备份路径和操作人；不要把备份提交 Git。

## 9. 仍需真实环境手工验证

- 实体手机扫码、弱网/断网切换和低端设备长列表。
- AWS Workshop 与 Game Portal 外部链路及真实 Code 消耗规则。
- feedback/live 主机的实际 volume 名称、备份磁盘容量、恢复耗时。
- 多 Staff 同时录入/接单时的现场分工与冲突处理节奏。
